# План независимой проверки из российской сети

> Требование задачи 5 и уточнение владельца: скрипты должны срабатывать на серверах GitHub Actions, а не на self-hosted runner. Не создавать платные ресурсы, не предполагать наличие российского VPS. Основной PR не блокируется.

## Статус: реализовано через Globalping (2026-09-20)

Вариант «внешняя российская точка» (раздел Б ниже) реализован в упрощённом виде **без какой-либо инфраструктуры**: роль российской точки выполняет публичная сеть пробов [Globalping](https://globalping.io) (`locations: [{"country": "RU"}]`). Всё исполняется на `ubuntu-latest`:

- Модуль `vpnmy/globalping.py` (Python 3.11+, `asyncio` + `aiohttp`) встроен в пайплайн `build_subscription` между локальной предпроверкой и глубокой проверкой.
- Авторизация: `Authorization: Bearer <token>`, токен из переменной окружения `GLOBALPING_TOKEN` (GitHub Secret).
- Бюджет: `ru_check_budget` (125 по умолчанию, потолок 5000) + динамическое урезание по `GET /v1/limits` (свободная квота аккаунта минус резерв 3) — два запуска в час укладываются в бесплатный лимит ~250/час; списание платных кредитов останавливает прогон.
- Параллельность: `asyncio.Semaphore` (12), поллинг `GET /v1/measurements/{id}` с `asyncio.sleep` (0.7 с + джиттер, не чаще 2 req/s на измерение — требование API).
- Отказоустойчивость: 429 → exponential backoff (1с→30с, джиттер) с учётом `Retry-After`/«retry in N seconds»; 5xx/сетевые сбои → backoff; 422 «нет RU-пробов» → «неизвестно», а не «блокировка»; общий дедлайн этапа 420 с.
- Вердикты: TCP-проверка порта (VLESS/VMess/Trojan) и ICMP-пинг (Hysteria2, т.к. UDP-портов в Globalping нет). «Заблокировано в РФ» только при подтверждении ≥2 независимыми RU-пробами; молчание ICMP — «неизвестно».
- Результат: `stats.json → ru_check` (+ `ru_ms` у каждого опубликованного узла), строка на странице статуса, Job Summary в Actions. Заблокированные узлы исключаются до Xray/Hysteria-проверки (экономия бюджета ядер) и считаются сетевым отказом в истории (`ru_blocked_streak`).

**Что это не решает (честно):** SNI-DPI TСПУ не детектируется чистым TCP-connect; пробы в РФ — дата-центры, а не мобильные/домашние сети Казани; Hysteria2 проверяется только ICMP. Эти варианты (российский прокси/опрашиваемый сервис) из разделов А/Б ниже остаются будущим улучшением, если потребуется сигнал «из реальной пользовательской сети». Шифр обмена с подписью/HMAC из раздела «Формат обмена» не применялся — результаты приходят из доверенного публичного API, а не от чужого сервера.

## Текущее состояние

- Проверка выполняется на GitHub-hosted runner (`ubuntu-latest`, сеть GitHub — обычно США/Европа). Успех там **не гарантирует** доступность из Казани/мобильной сети пользователя: 6 финских узлов из 12 `n/a` на скриншоте — пример расхождения.
- В репозитории **нет** российского VPS/self-hosted runner; по требованию владельца он и не должен требоваться.
- Любой план не должен требовать установки ПО на ПК пользователя и не должен публиковать приватные ключи/полные конфиги узлов в логах/артефактах.

## Цель отдельной проверки

Дать второй независимый сигнал «работает ли узел для пользователя в РФ», не заменяя существующую проверку из GitHub. Результат российской точки — дополнительный флаг с меткой времени/TTL, а не замена двойной HTTPS-проверке через туннель.

## Принцип: всё исполняется на GitHub Actions

**Любой** скрипт — и основная сборка, и российская проверка — запускается на `runs-on: ubuntu-latest` (GitHub-hosted). Никаких `self-hosted` runner. Если внешнего выхода в РФ нет, job корректно пропускается (`continue-on-error`/условие на секрете) и не ломает публикацию.

## Вариант без инфраструктуры (рекомендованный сейчас)

1. **Не блокировать PR.** В `stats.json` уже есть `verification` и `diversity`/`asn`. На странице статуса честно указывается: «проверено с GitHub runner — не эквивалентно домашней/мобильной сети РФ».
2. **Агрегировать анонимную обратную связь без секретов (опционально, всё равно на Actions).** Будущий эндпоинт на Actions может принимать только `{node_id, median_ms, jitter, country, checked_at, ttl}` по подписанному токену. Полный URI/UUID/пароль **не отправляются**, только `node_id` (хеш канонической ссылки) + метрики. Требуется: подпись (HMAC/Ed25519), привязка к `node_id`, проверка времени и TTL (600с), отклонение чужого/устаревшего.
3. **Не отправлять конфиги произвольным сервисам.** Внешним сервисам уходит только IP для ASN, не URI.

## Когда появится выход в РФ — интеграция без self-hosted

### А. Выход через российский HTTP/SOCKS-прокси (если владелец им располагает)

Если у владельца есть российский прокси (например, уже оплаченный/корпоративный, не создаём новый платный специально), проверка из РФ делается **тем же GitHub-hosted job**, но с прокси:

- Секреты: `RU_PROXY_URL` (например, `socks5://user:pass@ru.example:1080` или `http://...`), `RU_PROBE_TOKEN` для подписи результата. Если `RU_PROXY_URL` не задан — job делает `exit 0` без ошибки.
- Job `probe-ru` (`ubuntu-latest`, `timeout-minutes: 12`) ставит те же `xray`/`hysteria` (с проверкой SHA), далее запускает `python -m vpnmy.verify_ru --proxy $RU_PROXY_URL --publish data/ru_probe.json` — тот же `verify_all` с 3 измерениями, но трафик к `cp.cloudflare.com`/`success.txt` идёт через российский прокси/туннель. Таймауты те же (`verify_timeout_seconds` 8с, `verify_measurements` 3).
- Весь код исполняется на Actions; прокси — только транспорт. Логи не содержат URI/секретов.

### Б. Внешняя российская точка, опрашиваемая из Actions

Если есть отдельный российский сервис (уже существующий у владельца, не создаём новый), Actions job на `ubuntu-latest` просто **опрашивает** его по HTTPS:

- `GET https://probe-ru.example/api/check?node_id=...` с заголовком `Authorization: Bearer $RU_PROBE_TOKEN` (или HMAC). Сервис возвращает `{node_id, median_ms, jitter_ms, max_ms, egress_ip, checked_at, ttl_seconds, sig}`.
- Подпись проверяется в Actions (`HMAC-SHA256` по каноническому JSON + `RU_PROBE_TOKEN`). Без подписи/просроченный (`checked_at + ttl < now`) — отбрасывается.
- Снова: скрипт опроса живёт на `ubuntu-latest`, не на self-hosted.

### Формат обмена (общий)

```json
{
  "node_id": "abc123",
  "country": "DE",
  "median_ms": 680,
  "jitter_ms": 50,
  "max_ms": 700,
  "egress_ip": "1.2.3.4",
  "checked_at": "2026-09-15T12:00:00Z",
  "ttl_seconds": 600,
  "probe_id": "ru-via-actions",
  "sig": "hmac-sha256(...)"
}
```

- `node_id` — хеш канонического URI (host/port/UUID без имени/порядка полей); другой порт/host → другой `node_id`, старый результат не подходит.
- `checked_at` + `ttl_seconds` — срок годности 10 минут; `build_subscription` читает `data/ru_probe.json` только если свежо.
- Не публикуем полные URI/пароли; хранится только агрегированный флаг `ru_reachable` в `stats.json`/на странице.

### Workflow интеграция (только ubuntu-latest)

`workflow-templates/update-ru.yml` — шаблон с `runs-on: ubuntu-latest` (см. файл). Основной `update.yml` может опционально `needs: probe-ru` с `if: always()` и `continue-on-error: true`, чтобы отсутствие прокси/сервиса не ломало публикацию. Инструкции владельцу: скопировать шаблон в `.github/workflows/` через веб-интерфейс (Arena не имеет права `workflows`).

### Безопасность

- Не логировать/не передавать полные URI, `user`/`password`/`UUID`/`obfs-password`/`pinSHA256` за пределы job.
- Остаются лимиты `verify_measurements=3`, `verify_timeout_seconds=8`, `speed_test_bytes` один раз, чтобы уложиться в 12 минут вместе с основным job.
- Внешним сервисам — только IP для ASN, не секреты.

## Ограничения и честность

- Не обещать доступность из сети пользователя без измерения из соответствующей сети.
- Любая российская точка (даже дата-центр) — не эквивалент домашней/мобильной сети Казани; результат — лишь дополнительный замер.
- Чужие/устаревшие результаты не считаются подтверждением.

## Итог

Пока инфраструктуры нет — PR не блокируется, диагностика честно сообщает о месте проверки (GitHub-hosted). При появлении российского выхода — тот же Actions runner (`ubuntu-latest`) прозрачно добавляет российский сигнал через прокси или опрос сервиса, с подписью, TTL и без утечки секретов. Никаких self-hosted runner и установки на ПК пользователя не требуется.
