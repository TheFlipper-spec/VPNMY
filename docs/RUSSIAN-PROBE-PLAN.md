# План независимой проверки из российской сети

> Требование задачи 5: дополнительная удалённая точка проверки — только при наличии инфраструктуры.
> Не создавать платные ресурсы, не предполагать наличие российского VPS. Основной PR не блокируется.

## Текущее состояние

- Проверка выполняется на GitHub Actions runner в сети GitHub (обычно США/Европа). Успех там **не гарантирует** доступность из Казани/мобильной сети пользователя: 6 финских узлов из 12 `n/a` на скриншоте пример расхождения.
- В репозитории **нет** российского VPS, self-hosted runner или выделенного сервера в РФ.
- Любой план не должен требовать установки ПО на ПК пользователя и не должен публиковать приватные ключи/полные конфиги узлов.

## Цель отдельной проверки

Дать второй независимый сигнал «работает ли узел из сети РФ», не заменяя существующую проверку из GitHub. Результат российской точки не должен автоматически считаться истиной для всех пользователей, а должен храниться с меткой времени и источника, как дополнительный фактор для отбора или страницы статуса.

## Вариант без инфраструктуры (рекомендованный для сейчас)

1. **Не блокировать PR.** В `stats.json` уже есть поле `verification` и расширенная `diversity`/`asn` диагностика. Добавить в интерфейс/статистику пояснение: «проверено из GitHub runner, не эквивалентно домашней/мобильной сети РФ».
2. **Агрегировать анонимную обратную связь без секретов.** В будущих релизах можно добавить опциональный сбор обратной связи от добровольцев (например, через `POST /probe-result` с только `node_id`, `median_ms`, `jitter`, `country`, `checked_at`, `ttl`). Полный URI/пароль/UUID **не отправляются** — только идентификатор узла (hash) и метрики. Требуются: аутентификация (подписанный токен), привязка к `node_id`/`config` (хеш канонической ссылки), время проверки и срок годности (например, 10 минут), отклонение чужих/устаревших результатов.
3. **Не отправлять конфиги произвольным публичным сервисам проверки.** Любые внешние сервисы получают только IP для ASN, не URI.

## Если появится российская инфраструктура

### Подходящие варианты инфраструктуры (без платных предположений)

- **Self-hosted GitHub Actions runner** на уже существующем российском сервере владельца (если появится). Он может выполнять тот же `python main.py` или облегчённый `verify` шаг, публиковать результат в артефакт/ветку, а основной workflow агрегирует два отчёта.
- **Отдельный cron-контейнер/VM** с теми же `xray`/`hysteria` бинарниками, запускающий `verify_all` и публикующий `stats-ru.json` в тот же репозиторий или внешний объект-хранилище с ограниченным доступом.

Ни один вариант не требует установки ПО на ПК конечного пользователя.

### Интеграция результатов

1. **Формат обмена:** `{ "node_id": "abc123", "country": "DE", "median_ms": 680, "jitter_ms": 50, "max_ms": 700, "egress_ip": "1.2.3.4", "checked_at": "2026-09-15T12:00:00Z", "ttl_seconds": 600, "probe_id": "ru-runner-1", "sig": "HMAC(...)" }`. TTL — 10 минут; устаревшие (>TTL) не учитываются.
2. **Аутентификация:** runner подписывает результат ключом, известным основному процессу (GH secret `RU_PROBE_TOKEN` или Ed25519). Без подписи результат отбрасывается.
3. **Привязка к конфигурации:** `node_id` — хеш канонического URI (без имени/порядка полей); если узел изменён (другой порт/host/UUID), `node_id` меняется, старый результат не подходит.
4. **Хранение:** основной `build_subscription` читает `data/ru_probe.json` (если есть) и учитывает российский сигнал как дополнительный вес, **не заменяя** требование двойной HTTPS-проверки и стабильности. Например, помечает узел флагом `ru_reachable` для страницы статуса, но не публикует непроверенный из GitHub узел только потому что он «ответил в РФ».
5. **Время и сеть:** не заявлять, что VPS в дата-центре РФ эквивалентен домашней/мобильной сети Казани — разные маршруты, блокировки и NAT. Результат российской точки — лишь ещё один замер, а не гарантия для всех провайдеров.

### Безопасность

- Не логировать и не передавать за пределы runner полные URI, `user`/`password`/`UUID`/`obfs-password`/`pinSHA256`.
- Ограничить `verify_measurements` и `speed_test_bytes` на удалённой точке так же, как в основном workflow, чтобы уложиться в ресурсы.
- Таймауты: `verify_timeout_seconds` 8с, `verify_measurements` 3, `asn` 3с — аналогично основному.

### Workflow интеграция (когда инфраструктура появится)

- Добавить `workflow-templates/update-ru.yml` — шаблон с `runs-on: self-hosted` и лейблом `ru`, теми же шагами `install_xray`/`install_hysteria` и `python -m vpnmy.verify_ru --publish`.
- Основной `update.yml` может иметь опциональный `needs: probe-ru` с `continue-on-error: true`, чтобы отсутствие российской точки не ломало публикацию.
- Инструкции владельцу — скопировать `workflow-templates/update-ru.yml` в `.github/workflows/` через веб-интерфейс (Arena не имеет права `workflows`).

## Ограничения и честность

- Не обещать доступность из сети пользователя без измерения из соответствующей сети.
- Любая российская точка — лишь дата-центр, а не домашняя сеть; вариативность сохраняется.
- Чужие или устаревшие результаты не считаются подтверждением.

## Итог

Пока инфраструктуры нет — PR не блокируется, диагностика честно сообщает о месте проверки. План выше позволяет добавить российскую точку без платных предположений, с аутентификацией, TTL и без утечки секретов.
